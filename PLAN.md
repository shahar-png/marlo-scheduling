## Goal

When a guest books a host on production, the booking is real end to end and survives the guest changing their mind:

1. **Per-owner public URL (P1).** The booking page lives at `/{ownerSlug}/{eventSlug}` and every piece of page chrome and copy that names the host uses that host's `firstName` (title, hero, confirmation, email subject/body). `/demo/intro-30` remains only as the fixture-backed demo route; it is not the product URL. Event types are **owner-scoped**: two owners may both offer `intro-30`, and owner identity travels through the page, the form store, the API client, the availability route, the booking route, and the store (REV1-01).
2. **Durable booking row.** The booking persists in Neon (Postgres) across serverless isolates, and so do the owner, event-type, and schedule records it references, under **stable identifiers** — a fresh isolate can read a booking and resolve its event type and schedule (REV1-02). A booking has two distinct identifiers: an opaque `id` (the API path segment) and a separate secret `token` (the `/b/{token}` capability and the bearer credential for every `/api/bookings/{id}/*` call); the two are never equal and the id alone grants nothing (REV2-08). `GET /api/bookings/{id}` and `/b/{token}` return the same confirmed row regardless of which isolate serves the request. A create request carries a client-retained **idempotency key**, so a retry after a lost response returns the original booking and token instead of a second row (REV2-09).
3. **Live Google Calendar + real emails on book (P3).** Booking creates a real event on the host's connected primary calendar (`events.insert` with the host's stored OAuth refresh token) and sends a real confirmation email through the Gmail API to **both** the invitee and the owner, with a minimal `.ics`.
4. **Guest reschedule / cancel via `/b/{token}` (P2, P3 parity).** The guest's change path is the token page, not "reopen the event link and book again": the page carries explicit **Reschedule** and **Cancel** controls, its own authenticated availability that excludes the booking's current occupancy, and pending / conflict / error states wired to the real handlers (REV2-10). Reschedule moves the live calendar event (patch; or insert when the event is gone) and sends reschedule emails to invitee and owner. Cancel removes the live event and sends cancel emails. Calendar occupancy mutations happen **regardless** of the event type's legacy `notificationMode` (`calendar_invitation | email_confirmation`), which now only selects whether Google also sends its own attendee invitations (REV1-05).
5. **Honest failure semantics.** A booking whose DB write succeeded but whose email failed is still a booking: the API returns HTTP 201 with the booking token and `delivery.email: "failed" | "pending"`, and an idempotent, revision-aware retry route re-attempts delivery (REV1-07). Calendar failures and Gmail failures are distinguished in the response and in logs. Every lifecycle operation (create, reschedule, cancel) has a defined transaction order, durable operation state, compensation, and retry response (REV1-09), and never destroys a calendar event on the strength of an *unknown* commit outcome (REV1-10). Rev 3 makes that operation state complete: the operation's identity, its **ownership generation**, and the **intended calendar event id** are persisted before any Google mutation, so an accepted-but-lost insert or a process death is reconciled by the next call rather than duplicated or orphaned (REV2-03), a superseded worker reconciles the winner instead of undoing it (REV2-04), an unknown commit is only ever interpreted after the original transaction is known to have finished (REV2-02), and every conflict/capacity query sees pending reservations (REV2-01).

All live implementations sit behind interfaces whose default implementations are the existing in-memory / fixture / mock ones, so `PROOF_CMD` (`npm test`) stays green offline and never needs `DATABASE_URL`, Google, Gmail, or the network. Live code paths activate only when `DATABASE_URL`, `LIVE_CALENDAR=1`, and `LIVE_EMAIL=1` are set in the host environment **and** the database schema is current (AC-17).

## Non-goals

- Chrome / Gmail extension
- Host dashboard (listing/managing bookings as the host) — hosts see bookings on their Google Calendar and in their inbox; that is the dashboard for this slice
- Cursor cloud / any non-Vercel deploy target
- MJML / HTML email polish beyond the minimum plain-text body + `.ics` needed to send a real confirmation / reschedule / cancel
- Multi-calendar selection UI, calendar-picker, or writing to any calendar other than the host's primary
- Host self-serve creation/editing of event types (event types remain fixture-defined per owner and are materialized for an owner at sign-in; slugs are data, not a CRUD surface)
- Payments, SMS, reminders, buffer rules, round-robin / collective across hosts beyond the group-capacity check already in scope
- A background job runner / queue for email retry or for lifecycle reconciliation — retry and reconciliation are idempotent HTTP routes the guest or owner can hit from the confirmation page; no cron, no queue
- Exactly-once email delivery — at-least-once with a documented, bounded duplicate window (AC-13 / REV1-07)
- Durable (Postgres) single-use links or one-off meetings — the legacy `/api/links/{token}/*` entry point stays fixture-only and is refused in pg mode (C10 / REV2-11)
- A background reconciler for stuck `pending_op` rows — takeover happens on the next call that reads the row (C6.3)
- Changing the proof harness shape: `PROOF_CMD` remains `npm test` (typecheck + `next build` + unit tests via `scripts/proof.cjs`); the builder never edits `.github/`

## Interface contracts (normative; ACs reference these)

### C1. Owner-scoped identity (REV1-01, REV1-02)

- Every event type belongs to exactly one owner. Uniqueness in `lib/availability/event-type.ts` becomes `(ownerId, slug)`, not global `slug`. `createEventType` takes `ownerId`; existing fixture/test callers default to the demo owner.
- Stable identifiers are deterministic strings derived from slugs, identical in memory and pg mode: owner `own_{ownerSlug}`, event type `evt_{ownerSlug}__{eventSlug}`, schedule `sch_{ownerSlug}__{scheduleKey}`. Re-seeding fixtures in a fresh isolate reproduces the same ids, so a booking's persisted `eventTypeId`/`scheduleId` always resolves, and group-capacity counts never split across isolates.
- Owner records are created/updated on host sign-in: the OAuth callback upserts `owners` (slug = validated local-part of the Google email, `firstName` = profile `given_name`, `email`, `calendarId = 'primary'`) and materializes that owner's fixture-defined event types and schedule with the ids above. The `demo` owner is seeded by migration and by `ensureDemoFixtures()`.

### C3. Booking response envelope (REV1-06)

The shipped client (`lib/api/client.ts`) expects `{ booking: { … start … } }` on 201 and recognises 409 codes `slot_unavailable` and `session_full`. Rev 2 keeps that envelope and **adds** fields; it does not introduce `slot_taken`/`slot_full` (those names from rev 1 are withdrawn):

```json
201 {
  "booking": { "id", "token", "ownerSlug", "eventSlug", "start", "end", "status", "revision", "hostFirstName", … },
  "delivery": {
    "email":    "sent" | "failed" | "pending",
    "calendar": "created" | "failed" | "skipped" | "deleted",   // mirrors bookings.calendar_state (C6.8); "deleted" only on a cancelled booking
    "errors":   { "email"?: "gmail_send_failed" | "host_not_connected", "calendar"?: "calendar_insert_failed" | "host_not_connected" }
  }
}
409 { "error": "slot_unavailable" }   // overlap for this host (AC-4)
409 { "error": "session_full" }       // group capacity reached (AC-8)
409 { "error": "booking_changed" }    // versioned update lost / expectedRevision mismatch (AC-18)
409 { "error": "operation_in_progress", "retryAfterSeconds": n }  // another op owns pending_op (C6); also a same-key create replay while the original create is still active (C9) — NOT terminal for the client's key
409 { "error": "operation_superseded" } // this worker's op was taken over; winner's state reported in `booking` (C6)
409 { "error": "stale_revision" }     // notify for an older (revision, action) (C5)
400 { "error": "idempotency_key_required" }  // C9
422 { "error": "idempotency_key_reused" }    // C9: same key, payload differs from the immutable create fingerprint
410 { "error": "<SingleUseLinkConsumedError message>" }  // C10: consumed link with a *different* payload (existing wire status; identical payload replays 201)
501 { "error": "links_not_supported" }       // C10: one-off link in pg mode
503 { "error": "availability_unknown" }        // AC-7
503 { "error": "booking_outcome_unknown", "retryAfterSeconds": n }  // AC-11
```

`booking.id` and `booking.token` are **both** present and always unequal (C11). A create replayed with the same `Idempotency-Key` returns the **same** `booking` (same `id`, same `token`) with the current `delivery` and status 201 (C9). `PublicBooking` in `lib/api/types.ts` gains `id`, `ownerSlug`, `eventSlug`, `revision`, `delivery`; `mapBooking` maps `token` from `booking.token` (no longer from `booking.id`) and returns `null` when either `id` or `token` is missing. The client's `createBooking` posts to the owner-scoped route with the form's idempotency key and maps `delivery` through; the form's success path navigates on any 201 regardless of `delivery.email`.

### C4. Notification policy (REV1-05)

- **Recipients are a product constant, not a mode:** confirm, reschedule, and cancel each email **both** invitee and owner (P3). No `none | invitee | owner | both` mode exists or is introduced.
- **`notificationMode` (existing `calendar_invitation | email_confirmation`) selects only the Google attendee behaviour:** `calendar_invitation` → the calendar event lists the invitee as an attendee and `events.insert/patch/delete` are called with `sendUpdates=all` (Google sends its native invite/update/cancellation in addition to Marlo's emails); `email_confirmation` → no attendees, `sendUpdates=none`. Default for fixture event types is `email_confirmation`.
- **Calendar occupancy (insert on book, patch on reschedule, delete on cancel) is unconditional** in both modes and in both mock and live adapters.
- `dispatchBookingNotification` and `tests/notification.test.ts` are updated to this policy; the mock email adapter records `{ action, revision, recipient }` per send.

### C5. Delivery ledger (REV1-07)

`notification_deliveries (booking_id, revision, action, recipient) PK` with `state ∈ {claimed, sent, failed}`, `claimed_at`, `attempts`. One row per (revision, action, recipient); `revision` is the booking row's monotonically increasing `revision` column. Initial delivery and retries share one **atomic claim**:

```sql
INSERT INTO notification_deliveries (booking_id, revision, action, recipient, state, claimed_at, attempts)
VALUES ($1,$2,$3,$4,'claimed',now(),1)
ON CONFLICT (booking_id, revision, action, recipient) DO UPDATE
  SET state='claimed', claimed_at=now(), attempts=notification_deliveries.attempts+1
  WHERE notification_deliveries.state='failed'
     OR (notification_deliveries.state='claimed' AND notification_deliveries.claimed_at < now() - interval '2 minutes')
RETURNING attempts;
```

Only a caller that gets a row back sends. **The returned `attempts` value is the claim generation** (REV2-06): the sender keeps it and every finalisation carries it — `UPDATE … SET state=$s WHERE booking_id=$1 AND revision=$2 AND action=$3 AND recipient=$4 AND state='claimed' AND attempts=$gen`. A late finaliser whose claim was taken over after the 2-minute stale window (the row now carries `attempts = gen+1`) updates zero rows, logs `stale_finalize_ignored { bookingId, revision, action, recipient, gen }`, and never flips the new owner's row to `sent` or `failed`. `claim()` returns `{ gen }` and `finalize()` requires it in both stores; there is no finalisation path without a generation.

**Revision validation at claim time** (REV2-07): `bookings` carries `latest_action ∈ {confirm, reschedule, cancel}` written by the same T2 update that advances `revision` (C6). The notify route accepts two request forms and validates `(revision, action)` **together, under the booking's `FOR UPDATE` read inside the claim transaction**, never from a separate earlier read:

- **Revision-specific retry** — body `{ action, expectedRevision }` (the page/client always sends both, taken from the last `booking` it received): claims only if `bookings.revision = expectedRevision AND bookings.latest_action = action`; otherwise 409 `stale_revision` with the current `{ revision, latestAction }` in the body and nothing sent. `action` without `expectedRevision`, or `expectedRevision` without `action`, is 400 `notify_request_invalid`.
- **Explicit retry-latest** — body `{}` (neither field): the route resolves the booking's current `(revision, latest_action)` under the same lock and claims for exactly that pair; the response echoes which `{ revision, action }` it retried. This is the only form that can never be stale; it is what the "Resend" control uses when the client has no revision in hand (e.g. a reload of `/b/{token}`).

A send for `(revision, action)` older than the booking's current `(revision, latest_action)` is therefore refused before claiming (409 `stale_revision`) so a late confirmation can never mark a reschedule/cancel delivery sent or send stale content after a cancel. **Notify never inserts a calendar event on its own** (REV3-02): on a `status='cancelled'` booking the route only claims and re-sends `(revision, 'cancel')` rows and makes zero calendar calls, whatever `calendar_state` says; on a `status='confirmed'` booking with `calendar_state='failed'` it runs the owned calendar-repair operation of C6.8 (which is serialized with reschedule/cancel through `pending_op`) **before** the email claim, and reports the repair outcome in `delivery.calendar`. The in-memory store implements identical semantics with a synchronous map. **Unavoidable ambiguity:** if Gmail accepts the message and the `sent` write then fails, the row stays `claimed` and becomes re-claimable after 2 minutes → at most one duplicate per recipient per 2-minute stale window; documented in README. `delivery.email` summarises the current revision's rows: `sent` iff all recipients `sent`; `failed` if any `failed`; `pending` if any `claimed` and none `failed`.

### C6. Lifecycle state machine (REV1-08, REV1-09, REV1-10, REV2-01..05, REV3-01..03)

`bookings` carries `status ∈ {confirmed, cancelled}`, `revision int`, `latest_action`, `google_event_id`, `calendar_state` (C6.8), `reserved_start`/`reserved_end timestamptz null`, and `pending_op jsonb` (`null` or `{ kind: "create" | "reschedule" | "cancel" | "calendar_repair", opId: uuid, gen: int, startedAt, eventId?, newStart?, newEnd?, oldEventId?, fallbackEventId?, fenced?: string[] }`). Create, reschedule, and cancel all begin with the **same per-host serialization boundary**: `SELECT pg_advisory_xact_lock(hashtext($hostId))` in pg mode, a per-host async mutex in memory mode; under it they `SELECT … FOR UPDATE` the booking (lifecycle ops) and re-read `status`, `revision`, and `pending_op`. Every state-changing `UPDATE` is conditional on `id AND revision = $expected AND status = 'confirmed'`; zero rows → 409 `booking_changed`. The lock is held only for the duration of a transaction (T1, T2, T2′, reconciliation); **it is never held across a Google call** — durable reservations (below) make that unnecessary.

**C6.1 Durable reservations (REV2-01).** A slot is occupied from the moment a transaction that intends to use it commits, not from the moment the calendar or the final update succeeds. Occupancy for a host is the union of: (a) every `status='confirmed'` row's `[start, end)` — including rows whose `pending_op` is a `create` still awaiting its calendar step and rows whose `pending_op` is a `reschedule` (the **old interval is retained** until T2 or reconciliation releases it); and (b) every non-null `[reserved_start, reserved_end)` written by a reschedule T1 (the **destination is reserved durably** in T1). **Every** conflict and capacity query — create, reschedule, the owner-scoped availability route, the booking availability route, and the group-capacity count — is computed over this union, in both stores; the group count counts confirmed rows for the event type plus reservations targeting the slot. The one and only exclusion is *the booking's own* interval/reservation/managed event during its own reschedule (AC-8). A reservation is released only by the T2 that consumes it or by a T2′/takeover reconciliation that abandons it; a stale reservation (> 2 min) is reconciled by the next call that reads it, never silently ignored. Interleavings that must serialize correctly (proved in AC-4/AC-18): create vs. reschedule (a create into a reserved destination, or into a rescheduling booking's old slot, is 409 `slot_unavailable` until that reschedule completes or is abandoned); reschedule vs. reschedule across two different bookings (B may not reserve A's destination while A holds it, and may not reserve A's old slot until A's T2 commits); cancel vs. create (a booking under cancellation still occupies its slot until cancel T2).

**C6.2 Operation identity, intended event ids, idempotent inserts (REV2-03).** Every lifecycle operation writes `pending_op.opId` (fresh uuid), `pending_op.gen` (ownership generation, starts at 1), and — before any calendar mutation — the **exact Google event id it intends to create**, if it may create one: `pending_op.eventId` on create, `pending_op.fallbackEventId` on reschedule. Ids are generated app-side in Google's accepted alphabet (`[a-v0-9]{5,1024}`, derived as `marlo` + base32hex of a fresh uuid) and passed as the `id` field of `events.insert`, so an insert is **idempotent**: replaying it yields Google 409 `duplicate`, which the adapter maps to `AlreadyExists` and the caller treats as success after `events.get(id)` confirms the event carries this booking's `marloBookingId`. Because the intended id is durable before the call, an accepted-but-response-lost insert, a timeout, or a process death between the insert and the completing update is reconciled by the next call that reads the `pending_op`: `events.get(intendedId)` → present → proceed to the completing update; absent (404/410) → re-insert with the same id. Operation state is cleared **only** by the completing update, and only after the Google outcome is known; an ambiguous Google outcome (timeout, 5xx, network error) leaves `pending_op` in place and is resolved by `events.get` on the next attempt, never by a blind delete. Both calendar adapters (mock and live) honour client-supplied ids and `AlreadyExists`.

**C6.3 Ownership generations and takeover (REV2-04).** `pending_op.gen` is the operation's ownership generation. A worker that resumes a stale op (`startedAt` > 2 min ago, same or different kind per the policy in C6.6) takes ownership with `UPDATE … SET pending_op = pending_op || {gen: gen+1, startedAt: now()} WHERE id=$1 AND pending_op->>'opId'=$opId AND (pending_op->>'gen')::int=$gen` (zero rows → someone else took over first → 409 `operation_in_progress`). **Every** completing update (T2), clearing update (T2′), reservation release, and compensation is conditioned on `pending_op->>'opId'=$opId AND (pending_op->>'gen')::int=$gen` in addition to `revision`. A worker whose conditional update matches zero rows is **superseded**: it must not compensate, must not insert, must not delete, and must not clear anything. It re-reads the booking (fresh transaction, under lock) and **reconciles the winning operation**: if the row shows exactly the outcome it was trying to reach (reschedule: `status='confirmed'`, `revision` advanced, `start = newStart`; cancel: `status='cancelled'`) it returns that outcome (200) exactly as if it had done the work; otherwise it returns 409 `operation_superseded` with the current `booking`. A takeover begins by determining what the previous owner achieved from Google, not from memory: `events.get(oldEventId)` and, if set, `events.get(fallbackEventId)` / `events.get(eventId)`; the takeover then completes or abandons the op from that observed state (C6.4–C6.6). Before the **fallback insert** in reschedule, the worker re-verifies ownership under lock (`SELECT pending_op … FOR UPDATE`, opId/gen must match, `COMMIT`); a superseded worker that *observes* it is superseded never reaches `events.insert`.

**Event-id fence (REV3-01).** Database generations do not fence Google: a worker can pass the ownership re-check, pause, and issue its insert after a takeover; or its insert can be accepted by Google long after its own request timed out. Therefore a takeover **never abandons an operation, and a cancel never completes, while an intended event id of that operation is unresolved**. Every intended id (`pending_op.eventId`, `pending_op.fallbackEventId`) is resolved in exactly one of two ways before the abandoning T2′ or the cancel T2 may run: (1) **observed present** — `events.get(id)` returns a non-cancelled event carrying this booking's `marloBookingId` → the previous owner achieved it; the takeover *completes* the op against that event (never abandons it); or (2) **fenced** — the takeover claims the id at Google itself with `events.insert({ id, status: 'cancelled', extendedProperties.private.{ marloBookingId, marloFence: opId } , start/end = the op's interval, summary 'marlo-fence' })`. Because Google ids are unique per calendar for the lifetime of the calendar (a cancelled event keeps its id), a fence guarantees that any later insert with that id — by a paused or delayed worker — is answered 409 `duplicate`, so nothing live can appear behind the abandonment. Fence outcomes: 2xx → fenced; 409 `duplicate` → `events.get(id)`: cancelled fence → already fenced; live event → case (1), complete instead of abandon; **ambiguous** (timeout, 5xx, network) → the id is **unresolved**: the takeover stops, keeps `pending_op` (under its new `gen`, with `fenced` recording any ids already resolved), returns 503 `booking_outcome_unknown`, and the next call re-runs the fence (idempotent by id). Only after every intended id is present-or-fenced does the abandoning T2′ / cancel T2 run; it records the fenced ids in the row's `fenced_event_ids` (jsonb array, audit only). The **superseded worker's side**: `AlreadyExists` on its own insert is success **only if** `events.get(id)` returns a non-cancelled event with its `marloBookingId`; a cancelled event (a fence) means it was superseded → C6.3 reconcile path, zero further mutations. A fence is never deleted and never counted as occupancy (C7 ignores `status='cancelled'` items). The mock and live adapters and the fake `fetch` enforce id uniqueness across live **and** cancelled events (a re-used id is always 409 `duplicate`) and support inserting with `status='cancelled'`.

**C6.4 Create (two-phase, REV2-03, REV2-09, REV3-03, REV3-04).** T1 (under lock): C9 idempotency lookup (`SELECT … WHERE owner_id=$1 AND idempotency_key=$2`; row present → skip to *resume*); conflict/capacity check over C6.1 occupancy; `INSERT` (app-generated `id`, `token`, `idempotency_key`, `create_fingerprint` (C9), `status='confirmed'`, `revision=1`, `latest_action=NULL`, `calendar_state='pending'`, `google_event_id = intendedId`, `pending_op = {kind:'create', opId, gen:1, eventId: intendedId, startedAt}`) → `COMMIT`. The slot is now durably held. Calendar: `events.insert(id=intendedId, attendees per C4)`; `AlreadyExists` → `events.get` → live event with our `marloBookingId` → success (a cancelled fence → superseded, C6.3). T2 (under lock): `UPDATE latest_action='confirm', calendar_state='created', pending_op=NULL WHERE id AND revision=1 AND pending_op->>'opId'=$opId AND (pending_op->>'gen')::int=$gen` → `COMMIT` → email (C5, `revision=1`, `action=confirm`) → 201 with `booking` (incl. `token`) and `delivery`. **Resume** (same key retried, or any later lifecycle call that reads `pending_op.kind='create'`): if the op is **not stale** (`startedAt` within 2 min) another worker still owns it → 409 `operation_in_progress` with `retryAfterSeconds`, nothing written, no Google call (the client keeps its key and retries, C9); if stale → take ownership (C6.3), `events.get(eventId)` → present → T2; absent → insert with the same id → T2; then return 201 with the original booking and its current `delivery`. A create is **never abandoned**: its intended id is either completed or, when the row is cancelled by a takeover (C6.7), fenced. Failures: T1 `COMMIT` definite failure → nothing to compensate (no Google call has happened), 500 `booking_failed`, no token. T1 `COMMIT` unknown → C6.5 reconciliation by `(owner_id, idempotency_key)`: present → continue at the calendar step; absent → 500 `booking_failed`; unresolvable → 503 `booking_outcome_unknown` with `retryAfterSeconds` and no token (the client retries with the same key). Calendar **definite** failure (4xx other than 409, `host_not_connected`) → T2′ `UPDATE latest_action='confirm', calendar_state='failed', pending_op=NULL WHERE … opId/gen` → `COMMIT` → email (C5, `(1, 'confirm')` — the business creation is **finalized** exactly as on the success path; only the calendar outcome differs, REV3-03) → 201 with `delivery.calendar: failed`, `delivery.email` per the send (AC-10(d)). From that persisted state (`revision=1, latest_action='confirm', calendar_state='failed', pending_op=NULL`) both notify forms are valid (`{ action:'confirm', expectedRevision:1 }` and `{}` → `(1,'confirm')`), and the calendar is repaired only by the owned C6.8 operation (same intended id), never by an unowned insert. Calendar **ambiguous** failure (timeout, 5xx, network) → `pending_op` retained, 503 `booking_outcome_unknown` with `retryAfterSeconds`; the retry reconciles via `events.get`. T2 failure after a confirmed insert → `pending_op` retained; the retry resumes at T2 (no second insert: `events.get` first). Email failure after T2 → 201 with `delivery.email: failed`.

**C6.5 Unknown-outcome reconciliation (REV2-02).** An unknown commit outcome (SQLSTATE class `08`, socket `ECONNRESET`/`ETIMEDOUT`, or no server response) is **never** interpreted from a plain read: absence of a row or an unchanged `revision` proves nothing while the original transaction may still be in flight. The reconciler opens a **fresh connection**, sets `SET LOCAL lock_timeout = '5s'`, and reacquires the same per-host advisory lock (`pg_advisory_xact_lock(hashtext($hostId))`). Because the original transaction holds that lock until it commits or rolls back, a successful reacquisition **establishes that the original transaction has finished**; only then does the reconciler read (`SELECT … WHERE owner_id AND idempotency_key` for create T1; `SELECT revision, status, pending_op` for T2s). If the lock cannot be reacquired (lock timeout, connection error) or the read fails, the outcome stays **unknown**: no compensation, no clearing, `pending_op` (if any) retained, log `outcome_unresolved { bookingId, opId, gen }`, respond 503 `booking_outcome_unknown` with `retryAfterSeconds`. The memory store has the same boundary (await the host mutex, then read). The fake `Queryable` models **delayed commit completion**: a `COMMIT` whose response is lost while the server-side transaction stays open for a configurable time, holding the lock, and then commits or rolls back; a reconciler that reads before that resolution must block on the lock, and a test asserts that no compensation happens during the window.

**C6.6 Reschedule.** T1 (under lock): re-read FOR UPDATE; reject unless `status='confirmed'` and `revision = expectedRevision`; `pending_op` policy: `NULL` → proceed; `kind='reschedule'`, `'create'`, or `'calendar_repair'` and stale → take over (C6.3) and reconcile that op **first** (complete it from observed Google state, or — reschedule only — abandon it **after fencing its `fallbackEventId`** per C6.3; a create or repair is always completed, never abandoned), then proceed with this reschedule as a new op; not stale → 409 `operation_in_progress` (`retryAfterSeconds` = remaining stale window); `kind='cancel'` → 409 `operation_in_progress` regardless of age (a stale cancel is resumed only by a cancel call). Availability check for the new slot over C6.1 occupancy excluding this booking's own occupancy, with `start` validated as a candidate of the **reschedule slot increment** generator (C12, REV3-08 — the same generator the booking availability route uses, so every offered slot is accepted and nothing else is); `UPDATE pending_op = {kind:'reschedule', opId, gen:1, newStart, newEnd, oldEventId: google_event_id, fallbackEventId: intendedId, startedAt}, reserved_start=$newStart, reserved_end=$newEnd WHERE id AND revision=$r AND status='confirmed'` → `COMMIT`. Calendar: `events.patch(oldEventId, newTime)`; on 404/410 → ownership re-check under lock (C6.3) → `events.insert(id=fallbackEventId)` (`AlreadyExists` → `events.get`: live event with our `marloBookingId` → success; cancelled fence → superseded, C6.3). T2 (under lock): `UPDATE start, "end", rescheduled_from, google_event_id=$resultingId, calendar_state='created', revision=revision+1, latest_action='reschedule', pending_op=NULL, reserved_start=NULL, reserved_end=NULL WHERE id AND revision=$r AND pending_op->>'opId'=$opId AND (pending_op->>'gen')::int=$gen` → `COMMIT` → email (`action=reschedule`, new revision). Failures: patch/insert **definite** failure → T2′ (conditioned on opId/gen) clears `pending_op` and the reservation, booking unchanged, 502 `calendar_patch_failed` (retryable, no email) — a *definite* 4xx is Google's own rejection, so no fence is needed; only an **ambiguous** outcome can execute late, and that path retains `pending_op` so any later abandonment fences the id (REV3-01); **ambiguous** calendar failure → `pending_op` and reservation retained, 503 `booking_outcome_unknown`; the retry reconciles with `events.get`. T2 definite failure → compensate **only after** re-verifying ownership under lock (`patch` back to the old time, or `delete(fallbackEventId)`), `pending_op` stays for resume, 500 `reschedule_failed`. T2 unknown → C6.5 (reacquire lock, then read `revision`): advanced → success path; not advanced and still owner → compensate as above; superseded → C6.3. Email failure after T2 → 200 with `delivery.email: failed`; retry via notify route.

**C6.7 Cancel — one policy (REV2-05).** Cancel **never runs concurrently with a reschedule of the same booking and never undoes one.** T1 (under lock): re-read FOR UPDATE; reject unless `status='confirmed'` and `revision = expectedRevision` (409 `booking_changed` if a reschedule advanced `revision` — the page reloads and the guest cancels the new time). `pending_op` policy: `NULL` → proceed; `kind='cancel'` → resume (take over if stale, else 409 `operation_in_progress`); `kind='reschedule'`, `'create'`, or `'calendar_repair'` **not stale** → **refuse** with 409 `operation_in_progress` and `retryAfterSeconds` — the token page waits and retries, it does not race; **stale** → **take over the reschedule/create/repair first** (C6.3): from `events.get(oldEventId)` / `events.get(fallbackEventId)` / `events.get(eventId)` determine what was achieved — a moved or fallback-inserted event means the reschedule is completed via its own T2 (revision+1, `google_event_id` = resulting id); a create/repair whose event is present is completed via its T2; nothing achieved means the reschedule is abandoned via T2′ (reservation released) **only after its `fallbackEventId` is fenced** (C6.3), and a create/repair whose event is absent is **not** abandoned: the cancel fences `eventId` (so the paused inserter can never land) and then proceeds with the cancel against the fenced-or-absent id — and only then begin the cancel against the **resulting** event id under the new revision. `UPDATE pending_op = {kind:'cancel', opId, gen:1, oldEventId: google_event_id, startedAt} WHERE id AND revision=$r AND status='confirmed'` → `COMMIT`. Status stays `confirmed` and occupancy stays held until the event is gone. Calendar: `events.delete(oldEventId)` (404/410 tolerated; deleting a fence is a tolerated no-op). T2 (under lock): `UPDATE status='cancelled', calendar_state='deleted', revision=revision+1, latest_action='cancel', pending_op=NULL, reserved_start=NULL, reserved_end=NULL WHERE id AND revision=$r AND pending_op->>'opId'=$opId AND (pending_op->>'gen')::int=$gen` → `COMMIT` → email (`action=cancel`). A cancel T2 is permitted **only** when every intended id of the operation it took over is present-or-fenced (C6.3); an unresolved id leaves `pending_op` (kind `cancel`, now carrying the inherited ids) and returns 503 `booking_outcome_unknown`. Failures: delete definite failure → T2′ (opId/gen) clears `pending_op`, booking still confirmed, 502 `calendar_delete_failed` (retryable); ambiguous → retained, 503 `booking_outcome_unknown`. T2 definite/unknown failure after a successful delete → `pending_op` stays; the next cancel call resumes at T2 (delete of an already-deleted event is a tolerated 404), so the retry response is 200 `cancelled`. Consequently a reschedule that reads `pending_op.kind='cancel'` is refused with 409 `operation_in_progress`, a reschedule whose T2 finds its op taken over by a cancel returns 409 `operation_superseded` carrying the current booking (even when the takeover completed its move before cancelling — the row is now `cancelled`, which is not the outcome the reschedule was reaching for), and **no replacement event is ever inserted for a booking under cancellation or by a superseded worker** (REV1-08, REV2-04, REV2-05) — and, with the fence, a superseded worker's insert that *does* reach Google is answered 409 `duplicate` (REV3-01).

**C6.8 `calendar_state` transitions and the calendar-repair operation (REV3-02).** `calendar_state ∈ {pending, created, failed, deleted}` (schema `CHECK`), written only by the lifecycle transactions below — every lifecycle outcome names its transition:

| Transaction | `calendar_state` after |
|---|---|
| create T1 | `pending` |
| create T2 (event present) | `created` |
| create T2′ (definite insert failure) | `failed` |
| reschedule T1 | unchanged |
| reschedule T2 (patched or fallback-inserted) | `created` |
| reschedule T2′ (abandoned / definite failure) | unchanged (still `created` or `failed`) |
| cancel T2 | `deleted` (also when the delete was a tolerated 404, or the event was only a fence) |
| repair T2 | `created` |

`delivery.calendar` in every envelope mirrors this column (`created`/`failed`/`deleted`; `skipped` only when the calendar adapter is absent in memory mode). **Repair** is an explicit owned operation: `POST /api/bookings/{id}/notify` (either form), when the FOR UPDATE read under the host lock shows `status='confirmed' AND calendar_state='failed' AND pending_op IS NULL`, writes `pending_op = {kind:'calendar_repair', opId, gen:1, eventId: google_event_id, startedAt}` (conditioned on `revision` and `status='confirmed'`) → `COMMIT`; then `events.get(eventId)` → present → repair T2; absent → `events.insert(id=eventId)` (`AlreadyExists` → `events.get`; a cancelled fence → superseded); repair T2 (under lock): `UPDATE calendar_state='created', pending_op=NULL WHERE id AND revision=$r AND status='confirmed' AND pending_op->>'opId'=$opId AND (pending_op->>'gen')::int=$gen` → `COMMIT`; then the email claim proceeds for the current `(revision, latest_action)`. Definite insert failure → T2′ clears `pending_op`, `calendar_state` stays `failed`, `delivery.calendar: failed`, emails still retried; ambiguous → `pending_op` retained, 503 `booking_outcome_unknown`. Repair **never** runs on a cancelled row (the read shows `status='cancelled'` → email retry only, zero calendar calls). When notify's read shows a non-null `pending_op`: `kind='create'` → resume it per C6.4 (existing behaviour: non-stale → 409 `operation_in_progress`, stale → take over and complete); any other kind, stale or not → 409 `operation_in_progress` with `retryAfterSeconds`, nothing sent (stale reschedule/cancel/repair ops are taken over only by lifecycle calls, never by notify). Repair is itself subject to takeover by reschedule/cancel (C6.6/C6.7: a stale repair is completed from `events.get`, never abandoned; a cancel taking over a repair fences `eventId` if absent). A reschedule of a booking with `calendar_state='failed'` needs no repair first: its patch 404s and the fallback insert creates the event (T2 → `created`).

### C7. Calendar busy classification (REV1-03, REV1-04, REV3-10)

- External busy for the host's **primary** calendar is computed from `events.list` (`calendarId=primary`, `timeMin/timeMax` = the availability window, `singleEvents=true` so recurring series are expanded, `showDeleted=false`, `maxResults=250`, and a `pageToken` loop until `nextPageToken` is absent). An item is **managed** iff `extendedProperties.private.marloBookingId` is present (set on every Marlo insert/patch/fence). A managed item is excluded from external busy **only when the store accounts for it** (REV3-10): its `marloBookingId` resolves to a row of this host and the item's `[start, end)` equals that row's current `[start, end)` or its `[reserved_start, reserved_end)` (the row's committed or reserved occupancy, which C6.1 already counts). A managed item that is **unmatched** (no such row, a cancelled row) or **displaced** (a live event the host moved by hand in Google Calendar, so its interval matches neither the row's interval nor its reservation) is treated conservatively as **external busy** at its actual interval — the store's own occupancy for that row is still counted too, so a host-moved event blocks both its old and its new interval until the host fixes it; no calendar-to-store synchronization is attempted (Non-goals). Fences (`status='cancelled'`) are never busy. Every other item with `status != 'cancelled'` and `transparency != 'transparent'` is external busy; `dateTime` bounds are used as-is, all-day `date` bounds are converted in the host's timezone.
- `freeBusy.query` remains the read path for the existing multi-host (collective) availability in `lib/calendar/google-freebusy.ts`, and its fail-closed handling (AC-7) stays. Therefore the consent scope set is **exactly** `openid email profile https://www.googleapis.com/auth/calendar.freebusy https://www.googleapis.com/auth/calendar.events https://www.googleapis.com/auth/gmail.send` with `access_type=offline`, `prompt=consent` (REV1-04).
- Both `events.list` and `freeBusy` are fail-closed: non-2xx, a page that cannot be parsed, an item missing `start`/`end`, or a pagination loop that errors mid-way → `AvailabilityUnknown` → 503 `availability_unknown`.

### C9. Create idempotency key (REV2-09, REV3-04, REV3-05, REV3-06)

- The **client** owns the key **and the payload it was minted for**. `booking-form-store` generates one uuid (`crypto.randomUUID()`) when the guest starts a submission and persists an **unresolved-submission record** `{ key, payload: { ownerSlug, eventSlug, start, invitee: { name, email }, notes? }, startedAt }` in `sessionStorage` under `marlo:submission:{ownerSlug}/{eventSlug}` *before* the request is sent. Every replay sends the **stored** payload with the stored key, never the current form state.
- **Terminal vs. non-terminal responses (REV3-04).** The record is cleared **only** on: 201 (recovered or first-time success — the client navigates to `/b/{token}`); 400 (request rejected before any store write); 409 `slot_unavailable` / 409 `session_full` (the C9 lookup runs first under the lock, so either code proves no row exists for this key); 422 `idempotency_key_reused` (a row exists but is not this submission's — cannot happen for a stored-payload replay; treated as terminal, new key). The record is **retained** and the same key + payload are replayed on: 409 `operation_in_progress` (the original create is still active on another worker — **non-terminal**; the client waits `retryAfterSeconds` and replays, automatically once, then via "Try again"), 503 `booking_outcome_unknown`, any 5xx, a network error, and a page reload. A new key is minted only after a terminal response, or when the guest changes slot/invitee **and no unresolved record exists** (an unresolved record must be resolved or explicitly discarded first — see recovery).
- **Reload recovery (REV3-06).** On construction, `BookingFormStore` checks for an unresolved record for its `{ownerSlug, eventSlug}` **before** it loads availability: if one exists it enters `recovering` (form hidden behind "Finishing your booking…") and calls `client.recoverBooking({ key, payload })` — the same `POST` with the same header, but through a client entry point that **bypasses** the new-submission gates: no elapsed-start check (`lib/api/client.ts` `createBooking` keeps its check for new submissions), no requirement that `start` still appears in availability, no dependence on `selectedStart/name/email` (the constructor's reset of those fields is unchanged). Outcomes follow the terminal/non-terminal rule above: 201 → navigate to `/b/{token}` of the original row; 409 `operation_in_progress` → wait and replay; 503/5xx/network → `recovering` shows "Try again" (replay) and "Start over" (**explicit discard** of the record, logged `submission_discarded`, then normal flow); a terminal 4xx → record cleared, one notice ("Your earlier booking didn't go through"), normal flow with availability loaded. Only after the record is resolved or discarded does the store load availability and accept a new selection. The server keeps its own gates for **new** submissions only: the elapsed-start and availability checks in the create route apply when no row exists for the key; a replay whose row exists returns that row regardless of whether its start has elapsed.
- `lib/api/client.ts` `createBooking({ ownerSlug, eventSlug, body, idempotencyKey })` and `recoverBooking({ key, payload })` both send `Idempotency-Key`; the route requires it (400 `idempotency_key_required` when missing or not a uuid) and passes it to the store.
- **Server side.** The store keys idempotency on `(owner_id, idempotency_key)` (unique index, C8) and persists, in the create T1 `INSERT`, an **immutable `create_fingerprint`** (REV3-05): `sha256` of the canonical JSON `{ eventTypeId, start: <original start, ISO-8601 UTC ms>, inviteeEmail: <lower-cased, trimmed> }` — never recomputed, never updated by reschedule. `createBooking` looks the key up **first**, under the host lock: row present → compute the fingerprint of the *request* and compare with the stored one: **equal** → reconcile and return the **current** state of the original booking (resume the create per C6.4 if its `pending_op` is open — non-stale → 409 `operation_in_progress`, stale → take over; otherwise 201 with the same `id`, `token`, the row's *current* `start`/`revision`/`status` — a booking rescheduled from S to T replays as 201 with `start = T`, `revision = 2`; a cancelled one replays as 201 with `status='cancelled'`), **different** → 422 `idempotency_key_reused`, nothing written. The comparison never reads the mutable `bookings.start`. Never a second row, never a second calendar event.
- A committed-but-unreconciled outcome (T1 committed, the 201 never reached the client, the process died before the calendar step or T2) is therefore recoverable from **any** isolate and **any** later time: the retry finds the row by key, completes it, and returns the original token. The same path serves the legacy one-off link route in memory mode with the link token as the key (C10).

### C10. Legacy one-off link entry point (REV2-11)

- `POST /api/links/{token}/bookings` and `GET /api/links/{token}/available-times` (single-use links over `event_type` or `one-off meeting` targets, `lib/availability/single-use-link.ts`, `lib/availability/one-off.ts`) are **not** part of the live product surface: links and one-off meetings remain in-memory fixtures with no durable records, and are not materialized into Postgres (Non-goals).
- **Memory mode (`DATABASE_URL` unset):** behaviour is retained for fixtures/tests, but `bookSingleUseLink` no longer owns its own `tokenLocks` boundary or calendar ordering. It resolves the target, then calls the **shared** `BookingStore.createBooking` (C6.4 two-phase create under the per-host mutex, C6.1 reservation-aware conflict check, C9 key = `link:{token}`), and consumes the link inside T2 of that create (same mutex, same versioned update; consumption is **idempotent for the same booking** — the link records `consumedByBookingId`, and re-consuming for that id is a no-op). It therefore cannot bypass a host conflict created through the owner-scoped route, cannot double-book when two link bookings for the same host interleave, and cannot leave a calendar event behind when link consumption fails (consumption failure is a T2 failure → resume, not a rollback after a Google insert). **Consumed-link replay (REV3-09):** `resolveSingleUseTarget` no longer rejects a consumed link up front for `POST`. The `POST` handler resolves the link, then always enters the shared create with key `link:{token}`; the C9 lookup finds the original row → fingerprint equal → 201 with the original booking (a lost 201 is recoverable); fingerprint different → the handler maps 422 `idempotency_key_reused` to the existing **410** `SingleUseLinkConsumedError` response so the retained fixture test (`tests/single-use-route.test.ts`: reuse with a *different* start/invitee → 410) still holds. `GET /api/links/{token}/available-times` on a consumed link stays 410 (unchanged). `listSingleUseAvailableTimes` computes over C6.1 occupancy.
- **Pg/live mode (`DATABASE_URL` set):** both routes return 501 `links_not_supported` after resolving nothing — the check is the first statement in each handler, before the link lookup, before any store query, calendar call, or email. `/api/health` is unaffected. README lists the routes as fixture-only.

### C11. Booking id / token split and migration (REV2-08)

- **Today** `Booking.id` *is* the confirmation token (`lib/api/client.ts` `mapBooking` sets `token: booking.id`; `/b/{token}` reads `getBooking(token)`; `GET /api/bookings/{id}` takes the token as `{id}`). Rev 3 splits them: `Booking { id: 'bk_' + uuid, token: 32 random bytes base64url (43 chars) }` on both stores, generated by the store at create (`id <> token` is a schema check and a store invariant).
- **Store:** `BookingStore.getById(id)` and `getByToken(token)` (`SELECT … WHERE token=$1` in pg; a `byToken` index map in memory); lifecycle methods take `id` and are called only after the route has authenticated the token against the row.
- **Server adapter (`lib/api/server.ts`):** `getBookingByToken(token)` → `store.getByToken` (never `getById`); the `/b/{token}` page passes its path segment straight through, so a booking **id** in the `/b/` path renders the not-found shell.
- **Routes:** `/api/bookings/{id}` and every `/api/bookings/{id}/*` route resolve `getById(id)`, then require `Authorization: Bearer <token>` equal (constant-time) to `row.token`; missing header → 401 `token_required`; unknown id or mismatch → 404 `booking_not_found` (uniform, no enumeration). The token is never accepted in the query string or the JSON body.
- **Client (`lib/api/client.ts`):** `PublicBooking { id, token, … }`; `mapBooking` requires both `booking.id` and `booking.token` as strings and maps each explicitly; `getBooking({ id, token })`, `getBookingAvailability({ id, token, timeMin, timeMax })`, `rescheduleBooking({ id, token, start, expectedRevision })`, `cancelBooking({ id, token, expectedRevision })`, `retryNotification({ id, token, action?, expectedRevision? })` all set the bearer header. The confirmation navigation carries only the token (`/b/{token}`); the page obtains `id` from the row.
- **Fixtures/tests:** every fixture and test that built a booking with `id === token`, called `/api/bookings/{token}`, or navigated to `/b/{id}` is migrated; a grep-style test asserts no remaining `token: booking.id` / `getBooking(token)` in `lib/api/**` and `app/**`. `lib/api/DIVERGENCES.md` records the split.

### C12. `/b/{token}` controls and states (REV2-10, REV3-07, REV3-08)

- `app/(public)/b/[token]/page.tsx` renders, for a `confirmed` booking, a client component `BookingControls` with three explicit controls: **Reschedule** (opens the slot picker), **Cancel** (two-step: button → inline confirm), and **Resend confirmation** (existing AC-10 surface; sends the C5 retry-latest form when the page has no revision in hand, the revision-specific form otherwise). **Cancelled branch (REV3-07):** keeps its book-again anchor, renders **no Reschedule or Cancel control**, and renders the cancellation **delivery status** (`delivery.email` of the current revision: "Cancellation emails sent" / "…pending" / "…failed") plus a **Retry notification** control **iff** `delivery.email` is `pending` or `failed`. That control is the same resend surface (`retryNotification`): `{ action: 'cancel', expectedRevision }` right after an in-page cancel, `{}` after a reload; the server retries only the cancel emails and never inserts anything (C5, C6.8). This holds both for the immediate post-cancel render (the `done` state below) and for a fresh load of `/b/{token}` — there is no background delivery worker (Non-goals), so this control is the only retry path and must exist.

A 30-min booking at 09:00 under the normal fixture schedule is thus offered 09:15 (overlapping) and 09:30 (adjacent) among others; the booking's **current** start is excluded from candidates by both the route and the mutation (an unchanged-time reschedule is 409 `slot_unavailable`, never a calendar call). README documents the 15-minute reschedule grid. Selecting a slot calls `rescheduleBooking` with `expectedRevision = booking.revision`.
- **States** (a discriminated `controlsState`): `idle` · `pending` (an operation is in flight or the server answered 409 `operation_in_progress`: controls disabled, "Working on it…", automatic single retry after `retryAfterSeconds`) · `conflict` (409 `slot_unavailable`/`session_full` → picker refreshes availability and shows the recovery copy; 409 `booking_changed`/`operation_superseded`/`stale_revision` → reloads the booking via `getBooking` and shows "This booking changed elsewhere — showing the latest") · `error` (5xx, 502 `calendar_*_failed`, network → "Try again" keeps the same `expectedRevision`; 503 `booking_outcome_unknown` → "We're not sure that went through" with a reload action that re-reads the booking rather than re-submitting) · `done` (200 → the page re-renders from the returned `booking`, incl. the new time or the cancelled panel, and shows the `delivery.email` outcome with the resend / retry-notification control if not `sent` — on the cancelled panel too, REV3-07).
- All controls are proven **through the real handlers** via `handler-transport` (no mocked client): the tests drive the React components against the actual `app/api/bookings/[id]/*` routes with fake adapters and the lock-queue fake DB.

## Approach

Work proceeds in the order below; each step lands with its tests so `npm test` is green at every step.

### 1. Env + proof hardening first (AC-6, AC-15; LIVE-03, LIVE-09, REV1-12)
- `lib/env.ts` is the single reader: `resolveEnv(overrides?)` with `setEnvOverride()` for tests; `MARLO_PROOF=1` forces `store=memory, calendar=mock, email=mock`.
- `scripts/proof.cjs`: extract `provisionDependencies()` (the existing `npm ci` fallback) and `runProof()`; provisioning runs first, logs the network step, and exits 2 under `MARLO_OFFLINE=1`; `runProof` spawns typecheck/build/unit with the explicit disabled child env. Export the functions for the unit test (guarded by `require.main === module`). `.github/proof.yml` is not touched.
- Test-setup `fetch` guard throws on any non-localhost URL; grep test exception list contains only `app/api/health/route.ts`.

### 2. Owner-scoped identity + per-owner routing + host chrome (AC-1, AC-2, AC-14; P1, REV1-01, REV1-02)
- `lib/owners.ts`: `Owner { id, slug, firstName, email, calendarId }`, `stableIds(ownerSlug, eventSlug, scheduleKey)` (C1), `OwnerStore` (memory + pg), `resolveOwner(slug)`. `ensureDemoFixtures()` and the OAuth callback both go through `materializeOwner(owner)` which upserts the owner and its fixture-defined event types/schedule under stable ids.
- `lib/availability/event-type.ts`: `createEventType({ ownerId, slug, … })`, uniqueness on `(ownerId, slug)`, `resolveEventType(ownerId, slug)`; `getEventType(id)` resolves from the store in pg mode.
- Routes: `app/(public)/[slug]/[event]` treats `[slug]` as the owner slug (no alias/canonicalisation from event to host); `app/demo/intro-30` pins `owner=demo, fixture=true`. New `app/api/owners/[ownerSlug]/event-types/[eventSlug]/{available-times,bookings}`; legacy `app/api/event-types/[slug]/*` delegate with `ownerSlug='demo'` and 404 `owner_required` otherwise.
- `booking-form-store` carries `{ ownerSlug, eventSlug }`; `lib/api/client.ts` builds owner-scoped paths and maps the C3 envelope; `lib/api/DIVERGENCES.md` updated.

### 3. Schema, durable stores, host lock, capacity (AC-3, AC-4, AC-8, AC-17; LIVE-01, LIVE-05, REV1-02, REV1-11)

Same lock key for reschedule/cancel (C6). Memory store: per-host async mutex with identical observable ordering, `byToken` and `byIdempotencyKey` maps, and the same `pending_op`/reservation fields.
- `lib/booking/occupancy.ts`: one `hostOccupancy(store, hostId, window, { excludeBookingId? })` used by create, reschedule, both availability routes, and the group count — no second conflict query exists (C6.1).
- `lib/booking/ids.ts`: `newBookingId()`, `newBookingToken()`, `newCalendarEventId()` (Google alphabet), `constantTimeEqual`; `lib/booking/fingerprint.ts`: `createFingerprint({ eventTypeId, start, inviteeEmail })` (canonical JSON → sha256), written once in create T1 and read by the C9 replay comparison (REV3-05).

- `lib/booking/occupancy.ts` `externalBusy` takes the store's managed occupancy map so `listBusy` can classify each managed item as **matched** (excluded) or **unmatched/displaced** (busy) per C7 (REV3-10).
- Availability = `externalBusy(events.list, managed-excluded)` ∪ `managedBusy(hostOccupancy)`; group slots compare `count < capacity` from the store only.

### 4. Google adapters, busy classification, fail-closed reads, compensation + reconciliation (AC-7, AC-11, AC-14; LIVE-04, LIVE-08, REV1-03, REV1-04, REV1-10)
- `lib/google/calendar.ts`: `insert({ id, … })` / `get(id)` / `patch` / `delete` (all set `extendedProperties.private.marloBookingId`, attendees + `sendUpdates` per C4; `insert` always passes the client-supplied `id` and maps Google 409 `duplicate` → `AlreadyExists`; `get` maps 404/410 → `null`) and `listBusy(window)` implementing C7 pagination/classification; `lib/calendar/google-freebusy.ts` keeps fail-closed `freeBusy` for the collective path. Both throw `AvailabilityUnknown`. Calendar errors are classified `definite` (4xx other than 409/429) vs `ambiguous` (timeout, 5xx, 429, network) — the mock adapter exposes the same classes and honours client ids.
- `lib/google/oauth.ts`: refresh-token exchange with injected `fetch`; `invalid_grant` → `HostNotConnected`. `lib/auth/config.ts` scope list = C7 set; callback materializes the owner.
- `lib/booking/create.ts`: C6.4 two-phase create; `classifyCommitError(err)` → `definite | unknown`; `lib/booking/reconcile.ts` `withFinishedTransaction(hostId, fn)` implements C6.5 (fresh connection, `lock_timeout`, advisory lock reacquire, then `fn`), shared by create T1, reschedule T2, and cancel T2 unknown outcomes; `resumeCreate()` (`events.get` → insert-if-absent → T2) used by the key replay, notify, and any lifecycle call that reads `pending_op.kind='create'`. Logs `outcome_unresolved`, `operation_superseded`, `stale_finalize_ignored`, `event_id_fenced`, `submission_discarded`. There is no calendar delete on the create path at all. The calendar adapters gain `insert({ id, status: 'cancelled', … })` support and enforce id uniqueness across live and cancelled items; `lib/booking/fence.ts` `fenceEventId(id, opId)` implements the C6.3 fence (2xx → fenced; `duplicate` → `get` → live → `present`, cancelled → `fenced`; ambiguous → `unresolved`) and `resolveIntendedIds(op)` runs it for every intended id before any abandonment/cancel T2 (REV3-01).
- Fake `Queryable` gains: `commitOutcome: 'ok' | 'definite' | 'unknown-committed' | 'unknown-rolled-back' | { unknown: true, resolveAfterMs, as: 'commit' | 'rollback' }` (delayed completion holds the fake advisory lock until resolved), per-connection identity (to assert the reconciler used a fresh one), `lock_timeout` simulation, and a fake clock for the 2-minute stale window.

### 5. Email: validation, MIME/ICS, dual recipients, delivery ledger (AC-5, AC-10, AC-13; LIVE-02, LIVE-07, LIVE-10, REV1-05, REV1-06, REV1-07)
- `lib/email/address.ts` strict single-mailbox parser (400 at the API boundary); `lib/email/mime.ts` RFC 2047 / quoted-printable / base64 `.ics`; `lib/email/ics.ts` RFC 5545 escaping.
- Templates `confirm` / `reschedule` / `cancel` × `invitee` / `owner`; cancel intro is its own constant with a disjointness test.
- `lib/notify/ledger.ts`: `claim({ bookingId, revision, action, recipient }) → { gen } | null` / `finalize({ …, gen, state })` per C5 on both stores (finalisation without `gen` is a type error); `lib/notify/dispatch.ts` sends to both recipients for every action, threads `gen` from claim to finalize, and consults `notificationMode` only for attendees/`sendUpdates`. `POST /api/bookings/{id}/notify` parses the two C5 request forms, reads the booking `FOR UPDATE` inside the claim transaction, validates `(expectedRevision, action)` against `(revision, latest_action)` together, claims per recipient, and refuses stale pairs with the current pair in the body; it also runs `resumeCreate()` when `pending_op.kind='create'`, returns 409 `operation_in_progress` for any other live `pending_op`, and — on a confirmed row with `calendar_state='failed'` and no `pending_op` — begins the owned `calendar_repair` op of C6.8 (`lib/booking/repair.ts`: T1 writes the op, `events.get` → insert-if-absent with the persisted id, owned T2 sets `calendar_state='created'`) before the email claim; on a cancelled row it never calls the calendar (REV3-02). ## Assumptions and risks

- **Assumption:** the host's Google account grants `calendar.freebusy`, `calendar.events`, and `gmail.send` in one consent; sending "as the host" via Gmail API is acceptable to the Founder for this slice (no custom domain / SES).
- **Assumption:** an owner's slug is the validated local-part of their Google email; a collision on sign-in (two accounts with the same local-part) fails the sign-in with `owner_slug_taken` rather than silently suffixing. Documented in README.
- **Assumption:** `events.list` on the host's primary calendar returns every occupying item within the window when `singleEvents=true` is used; items on secondary calendars are out of scope (Non-goals).
- **Risk — Next env reload (LIVE-03):** `next build` re-reads `.env.local`; mitigated by the explicit disabled child env plus `MARLO_PROOF=1` hard override; the fetch guard fails the proof loudly rather than silently going live.
- **Assumption — Google client-supplied event ids:** `events.insert` accepts an `id` in `[a-v0-9]{5,1024}` and answers 409 `duplicate` for a reused id; this is what makes inserts idempotent (C6.2). The live adapter is proven against a fake `fetch` that enforces the alphabet and the duplicate response; the Founder live smoke confirms it against Google.
- **Assumption — Google event ids are never recycled (the fence, REV3-01):** an `events.insert` with an `id` that already belongs to a *cancelled* or *deleted* event on the same calendar is answered 409 `duplicate`, exactly as for a live one, and `events.insert` accepts `status: 'cancelled'`. This is what turns the fence into a guarantee against paused or late inserts. Proven against the fake `fetch` (which enforces it) and confirmed by the Founder live smoke (insert → delete → re-insert same id → 409). If Google ever recycles ids, the fence degrades to the rev-3 ownership check and the live smoke catches it before ship.
- **Risk — Neon advisory locks under pooling:** `pg_advisory_xact_lock` is transaction-scoped and safe under PgBouncer transaction pooling; the builder must not use session-level locks. The lock is **never** held across a Google call (rev 3 two-phase create); the C6.5 reconciler's reacquisition is bounded by `lock_timeout = 5s`, after which the outcome stays unknown (503) rather than guessed.
- **Risk — at-least-once email:** a Gmail-accepted send whose `sent` write fails is re-sent after the 2-minute stale window (C5); accepted and documented. Late finalisers after a takeover are ignored by generation (REV2-06).
- **Risk — `pending_op` stuck when a process dies mid-operation:** the slot stays held (C6.1) and the op is taken over by the next call that reads it after the stale window (`gen+1`, reconciled from observed Google state); a different-kind call before that is refused with `operation_in_progress` + `retryAfterSeconds` and the token page waits. A create whose guest never retries leaves a confirmed row holding its slot with a possibly missing calendar event until any lifecycle/notify call reconciles it — accepted for this slice (the owner sees nothing until then; documented). No background reconciler by design.
- **Risk — Google patch vs host deletion race on reschedule:** a 404/410 on patch inserts a replacement with the persisted `fallbackEventId` after an ownership re-check; a duplicate is possible only if the host manually re-adds the event — accepted.
- **Risk — host edits Marlo events by hand (REV3-10):** a managed event the host moved in Google Calendar blocks both its old interval (store) and its new one (conservative external busy) until the host moves it back or the guest reschedules through `/b/{token}`; no sync is attempted. Accepted and documented in README.
- **Risk — fence placeholders on the host calendar:** a fence is a `status='cancelled'` event and is invisible in Google's default views; it is never counted as busy and never deleted. Accepted; documented.
- **Risk — idempotency-key replay window:** keys are retained forever on the row (no expiry); a guest replaying an old key gets the old booking, which is the intended behaviour; a different payload under an old key is 422. Accepted.
- **Risk — encryption key rotation:** `OAUTH_TOKEN_KEY` rotation is not handled; documented as a manual re-connect.
- **Scope risk:** AC-1/2/10 touch the front-end shipped in BOOK-FE (#38). The builder must keep the BOOK-FE mobile/CSS tests green; no visual redesign.
