Spec owner: Shahar + VP of Product · Product review: Shahar + Grok · Plan review: Codex (BLOCKED → revised → REVISE → revised → REVISE → revised → REVISE → revised → IMPL #27 shipped → Codex inspect REVISE → reverted #28 → revised → REVISE → revised → REVISE → revised) · Status: APPROVED Founder go + VP Product (plan revise after Codex REVISE BOOK-FE-14), 20 Sep 2026 ET

## Goal

An invitee can open a **public booking route**, pick a date/slot, enter name/email, and confirm a booking — **Marlo-branded UI** from the FE handoff — wired to the **existing** in-repo booking APIs. `https://marlo-scheduling.vercel.app` is no longer a placeholder-only homepage: `/` is branded cream/ink/lime chrome that links to a bookable demo, and `/{slug}/{event}` is a real booking page. After confirm, `/b/{token}` shows a branded “Handled.” confirmation shell. All handoff↔repo mapping lives in `lib/api/` (components never `fetch`). The page never offers, keeps offering, selects, or confirms a start that has already elapsed — the cutoff is re-evaluated against a **fresh clock** when availability resolves, while the picker stays open, at selection, and at submit. Production dependencies (API helpers, router navigation, clock) are created **inside client components**; the Server page passes only serializable props. An availability window that has fully elapsed yields empty availability, never a backend error. A group session whose last seat is taken (409 `session_full`) recovers the same way a taken 1:1 slot does — branded copy, selection cleared, availability refreshed. One submit gesture produces **at most one** `createBooking` call: while a request is in flight (and after success, until navigation completes) the submit control is disabled and any re-entry into the submit handler is a synchronous no-op, so a double-click or repeated Enter never creates two bookings. The picker has **one notion of "month"**: the displayed time zone's. The initial month, the `getSlots` query bounds, the day grouping, and month-boundary recovery all use the same displayed time zone (never UTC when the invitee is not in UTC), so a start that is Oct 1 on the invitee's wall clock is listed under October and is found by the October query — for any positive or negative UTC offset. A month is a window of **start** instants: a meeting that starts inside the displayed local month but ends after local month-end still belongs to that month and is still offered — the `lib/api` adapter widens the backend query's upper bound by the event duration (the existing slot engine excludes any meeting whose *end* exceeds `timeMax`) and then filters the returned starts back to the logical month window, so no bookable start disappears from both months. A malformed email address never reaches the backend: syntax is validated in the form before `createBooking` — one `@`, a non-empty local part, a domain of at least two dot-separated labels **every one of which is non-empty** (`a@b..co`, `a@.b.co`, `a@b.co.` are rejected), and no whitespace — `details.errors.email` is shown, the selected slot is kept, and the submit latch is released so the invitee can correct it. The confirmation page reflects the booking's `status`: active copy and meeting details only for a `confirmed` row; a row cancelled through the existing cancel route renders the existing cancellation copy inside the same branded shell. The cancelled shell never carries a broken link: `cancel.bookAgain` is rendered **only** when the adapter resolves a valid public booking URL for a reusable event type; a cancelled one-off booking (made through the existing single-use-link path, whose synthetic event type is not in the event-type store) keeps the cancellation shell and simply omits the link.

- Risk (BOOK-FE-12): applying the widening before the empty-range guard (comparing the clamped `timeMin` with `timeMax + duration`) re-opens an elapsed window and sends a `timeMin >= timeMax`-adjacent query to the slot engine for a month that is over. Guard on the original `timeMax` first; widen only a query that will actually be sent.
- Risk (BOOK-FE-12): "fixing" this by changing `end > timeMax` to `start >= timeMax` in `lib/availability/slots.ts` changes what the existing available-times route returns for every caller and breaks the BOOK-core / GRP / COL expectations that a slot must fit inside the window. Backend semantics are a non-goal; the adapter absorbs it.
- Risk (BOOK-FE-13): a domain character class that includes `.` (`[^\s@]+\.[^\s@]+`) satisfies "has a dot" but not "non-empty labels" — `a@b..co`, `a@.b.co`, `a@b.co.` pass, reach `normalizeInvitee` (which only wants an `@`), and become a booking plus a calendar attendee that can never be invited. - Risk (BOOK-FE-11): `if (booking)` as the confirmation branch condition shows “Invite's on its way” and the meeting time for a row the invitee cancelled a minute ago; the calendar event is already gone. - Risk (BOOK-FE-11): writing `"Canceled."` (or `"Handled."`) as a literal in the page file to satisfy the render fails AC-5's source assertions — both strings come from `copy/en.json` via `t()`.
- Risk (BOOK-FE-14): resolving `booking.eventTypeId` with a non-null assertion (`getEventType(id)!.slug`) or an unguarded property read makes the cancelled page throw (a 500 for the invitee) on any one-off booking, because the synthetic event type from `bookSingleUseLink` is not in the store. - Risk (BOOK-FE-14): "fixing" the null lookup by building the link from the synthetic `slug` (`/{host}/one-off-{id}`), from the raw `eventTypeId`, or from the one-off meeting store sends the invitee to a public booking page that 404s / cannot resolve the event — a broken link is worse than no link. - Risk (BOOK-FE-14): inserting the synthetic one-off event type into the event-type store so the lookup "works" changes `listEventTypes` / slug uniqueness semantics for the OFF and single-use tests and exposes a consumed single-use meeting as a reusable public event — backend semantics are a non-goal; absorb it in the confirmation adapter.
- Risk (BOOK-FE-14): substituting the missing link with a link to `/` or `href="#"` under the `cancel.bookAgain` copy misrepresents the action ("Book a new time" that books nothing); omit the anchor and add no copy.
