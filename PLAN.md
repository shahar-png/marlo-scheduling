# PLAN — LIVE-INT: durable booking store + live Google Calendar create + real confirmation email

Spec owner: Shahar + VP of Product · Product review: Shahar + Grok · Plan review: Codex (pending) · Status: DRAFT — Founder GO 21 Sep 2026 ET via VP Product; awaiting plan review

## Goal

When a guest books `/demo/intro-30` on production, three things are true that are not true today: (1) the booking row **persists across serverless isolates** — `GET /api/bookings/{id}` and `/b/{token}` return the same confirmed row no matter which isolate serves the request; (2) a **real Google Calendar event** is created on the host's connected calendar through `events.insert` using the host's own OAuth refresh token, obtained and stored when the host signs in at `/signin`; (3) the invitee receives a **real confirmation email**, sent as the host through the Gmail API, with the meeting details and a minimal `.ics` — not a row in the in-memory mock's `sent[]`. All three sit behind interfaces whose **default implementations are the existing in-memory / fixture / mock ones**, so `PROOF_CMD` (`npm test`) stays green offline; the live implementations activate only when `DATABASE_URL`, `LIVE_CALENDAR=1`, and `LIVE_EMAIL=1` are set in the host environment. README documents every env name and flag, and the live smoke (real Google + real inbox) is a Founder-run manual step, not an AC.

## Non-goals

- Chrome / Gmail extension
- MJML / HTML email polish beyond the minimum body needed to send a real confirmation (plain text + `.ics`; no template engine, no brand HTML)
- Full host dashboard / NavRail / event-type editor (the `/host` page gains only a connection-status summary)
- Cursor cloud agents (Mac-mini agent-os only)
- Changing BOOK-FE UI, brand, copy, or `lib/api` client shapes except the wiring that already exists (the booking POST body stays `{ start, invitee: { name, email } }`; no invitee timezone capture this slice)
- Full workflow / reminder suite; reminders, host "new booking" notice, bounce ingestion (confirmation on create — plus the existing reschedule/cancel emails through the same provider — is enough this slice)
- Durable event types, schedules, one-off meetings, single-use links, webhooks, reminders, or `notification_log` — those stay in-memory; only `bookings` and `host_google_tokens` are persisted
- A migration framework (one idempotent `db/schema.sql` applied by `npm run db:migrate` is enough)
- Multi-host live calendars (collective event types with several live hosts), Microsoft/other providers, `events.watch` push channels, free/busy caching
- A server-side idempotency key for the public booking POST (still deferred per `lib/api/DIVERGENCES.md`); cross-isolate race guard for **reschedule** (create is guarded; reschedule is not on the public BOOK-FE path)
- Rate limiting, captcha, token rotation UI, `needs_reauth` host notifications (the state is recorded and surfaced on `/host`; nobody is emailed)
- Changing `/api/health` (it must stay a dependency-free `{ ok: true }` so a bad `DATABASE_URL` cannot auto-revert a deploy through the health probe)
- Editing `handoff/**`, `.github/**`, `PLAN-REVIEW-LOG.md`

## Acceptance criteria

Every criterion is observed **only** via `PROOF_CMD` (`npm test`). The proof harness (`scripts/proof.cjs`) folds typecheck + `next build` + unit tests into `npm test`; keep that. No AC requires a database, Google, Gmail, or the network: live implementations are proven against injected fakes (a recording `Queryable` for SQL, a fake `fetch` for Google). The real-inbox / real-calendar check is the **Founder live smoke** in `## Verification`, which is manual and not graded.

## Approach

Files, in build order. Each step keeps `npm test` green on its own so a partial round is still inspectable.

1. **Store interface + memory default** (`lib/booking/store.ts`, `lib/runtime/live-config.ts`, `lib/runtime/live.ts`).

## Assumptions and risks

- **Founder + VP Product GO 21 Sep 2026 ET.** Stack: Next 16 App Router on Vercel (Node runtime for all route handlers — none declares `runtime = 'edge'`), Neon Postgres via `pg` over TCP to the pooled connection string, Google Calendar v3 + Gmail v1 REST via `fetch`, Auth.js v5 beta with JWT sessions (source: `package.json`, `lib/auth/config.ts`, `auth.ts`).
- **Why `pg` over `@neondatabase/serverless`:** the advisory-lock transaction (AC-4) needs an interactive transaction on one connection; `pg` gives that with the standard `Pool`/`PoolClient` API and no WebSocket shim, works against Neon's pooler and any local Postgres, and is pure JS. Cold-start cost of a TCP connect per isolate is acceptable at this traffic. If Vercel functions cannot reach Neon over TCP in the Founder's project, switch to `@neondatabase/serverless` `Pool` (same `query`/`connect` shape — the `Queryable` interface is chosen so only `lib/runtime/live.ts` changes).
- **Race guard scope:** `pg_advisory_xact_lock(hashtext(key))` serialises inserts per `host:start` across isolates; the overlap `SELECT` inside the lock catches non-equal-start overlaps (60-min vs 30-min). Hash collisions on `hashtext` only over-serialise, never under-serialise. The calendar event is created **before** the insert (today's order), so a lost race costs one compensating `deleteEvent`; a failed compensation leaves an orphan event on the host calendar and a 409 to the guest — logged, not retried (idempotent reconciliation via `extendedProperties.private.booking_id` is a later slice).
- **Two isolates, two event-type maps:** event types and schedules are in-memory and seeded on request; the deterministic demo ids (AC-10) keep `bookings.event_type_id` resolvable. Non-demo event types created in-process on one isolate are still invisible to another — unchanged from BOOK-FE and out of scope.
- **`notification_log` and webhook deliveries stay in-memory** (non-goal); the durable signal for "email sent" in the live smoke is the inbox and the host's Gmail Sent folder; the durable signal for the calendar is the event on the calendar.
- **Auth.js callback shape:** `jwt({ token, account, profile })` receives `account.refresh_token`, `account.scope`, `profile.email` on the initial sign-in in Auth.js v5 (`next-auth@5.0.0-beta.32`). `persistGoogleSignIn` is written against a narrow `{ account?: { provider; refresh_token?; scope? }, profile?: { email? } }` type so a beta shape drift is a one-line adapter, not a redesign.
- **Refresh token issuance:** Google returns `refresh_token` only with `access_type=offline` and, for an already-consented user, only when `prompt=consent` is sent — hence `prompt: 'consent select_account'`. The host sees the consent screen on every sign-in; acceptable for one host this slice.
- **Scopes:** `calendar.freebusy` + `calendar.events` (existing) cover `freeBusy` and `events.insert/patch/delete` on the host's own calendar; `gmail.send` covers `messages.send`. The OAuth app is Internal to `myoli.co`, so no Google verification is needed for these sensitive scopes (spec `AUTH-01`). The Calendar API and Gmail API must be **enabled** on the Google Cloud project — a live-smoke prerequisite, not code.
- **Edge bundle:** `middleware.ts` compiles for the edge; after the split it imports only `next-auth` + `lib/auth/config.ts` (+ `workspace.ts`, `host-guard.ts`), none of which import `pg`, the token store, or `lib/runtime/live.ts`. `token-crypto.ts` uses Web Crypto so it would be edge-safe anyway.
- **Email times in UTC** (no invitee timezone in the POST body — a BOOK-FE non-goal that this slice does not reopen). The `.ics` carries the exact instants, so the invitee's mail client shows local time on add-to-calendar. The demo schedule is UTC, so for the smoke the UTC text is also the host's wall time.
- **Gmail quotas / deliverability:** one host, one confirmation per booking — far below the Workspace daily cap; mail from the host's real Workspace address to a real inbox is the lowest-spam-risk path available without DNS work.
- **`TOKEN_ENCRYPTION_KEY` rotation** is a non-goal: rotating it invalidates stored rows, which then read as decrypt failures → treated like `needs_reauth` (the host re-signs in). Documented in README.
- **Proof stays offline by construction, not by convention:** `scripts/proof.cjs` deletes the five live names; `resolveLiveConfig` is pure; `pg` and the Google providers are only reachable behind `getLiveConfig()` branches that the deleted names can never enable. An inspector can verify this with the AC-5 grep and the absence of any `fetch(` to a Google host outside `lib/calendar/google-live.ts`, `lib/notify/gmail-live.ts`, `lib/auth/google-token-source.ts`.
- **Vercel deploy:** pushes to `main` deploy automatically. Until the Founder sets the env vars, production runs exactly as today (memory / fixture / mock) — the flags default off, so the merge itself changes nothing observable on prod except the demo event type's mode (`email_confirmation`: the mock "sends", the `/b/{token}` copy already says "Invite's on its way").
