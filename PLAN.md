# PLAN — LIVE-INT (rev 2): durable bookings, live Google Calendar, real emails, per-owner URLs, token reschedule

Spec owner: Shahar + VP of Product · Product review: Shahar + Grok · Plan review: Codex (LIVE-01..10 in rev 1; REV1-01..12 addressed below) · Status: REVISED — Founder GO 21 Sep 2026 ET; product locks P1–P3 verified by Founder and unchanged in rev 2

## Goal

When a guest books a host on production, the booking is real end to end and survives the guest changing their mind:

1. **Per-owner public URL (P1).** The booking page lives at `/{ownerSlug}/{eventSlug}` and every piece of page chrome and copy that names the host uses that host's `firstName` (title, hero, confirmation, email subject/body). `/demo/intro-30` remains only as the fixture-backed demo route; it is not the product URL. Event types are **owner-scoped**: two owners may both offer `intro-30`, and owner identity travels through the page, the form store, the API client, the availability route, the booking route, and the store (REV1-01).
2. **Durable booking row.** The booking persists in Neon (Postgres) across serverless isolates, and so do the owner, event-type, and schedule records it references, under **stable identifiers** — a fresh isolate can read a booking and resolve its event type and schedule (REV1-02). `GET /api/bookings/{id}` and `/b/{token}` return the same confirmed row regardless of which isolate serves the request.
3. **Live Google Calendar + real emails on book (P3).** Booking creates a real event on the host's connected primary calendar (`events.insert` with the host's stored OAuth refresh token) and sends a real confirmation email through the Gmail API to **both** the invitee and the owner, with a minimal `.ics`.
4. **Guest reschedule / cancel via `/b/{token}` (P2, P3 parity).** The guest's change path is the token page, not "reopen the event link and book again". Reschedule moves the live calendar event (patch; or insert when the event is gone) and sends reschedule emails to invitee and owner. Cancel removes the live event and sends cancel emails. Calendar occupancy mutations happen **regardless** of the event type's legacy `notificationMode` (`calendar_invitation | email_confirmation`), which now only selects whether Google also sends its own attendee invitations (REV1-05).
5. **Honest failure semantics.** A booking whose DB write succeeded but whose email failed is still a booking: the API returns HTTP 201 with the booking token and `delivery.email: "failed" | "pending"`, and an idempotent, revision-aware retry route re-attempts delivery (REV1-07). Calendar failures and Gmail failures are distinguished in the response and in logs. Every lifecycle operation (create, reschedule, cancel) has a defined transaction order, durable operation state, compensation, and retry response (REV1-09), and never destroys a calendar event on the strength of an *unknown* commit outcome (REV1-10).

All live implementations sit behind interfaces whose default implementations are the existing in-memory / fixture / mock ones, so `PROOF_CMD` (`npm test`) stays green offline and never needs `DATABASE_URL`, Google, Gmail, or the network. Live code paths activate only when `DATABASE_URL`, `LIVE_CALENDAR=1`, and `LIVE_EMAIL=1` are set in the host environment **and** the database schema is current (AC-17).

## Non-goals

- Chrome / Gmail extension
- Host dashboard (listing/managing bookings as the host) — hosts see bookings on their Google Calendar and in their inbox; that is the dashboard for this slice
- Cursor cloud / any non-Vercel deploy target
- MJML / HTML email polish beyond the minimum plain-text body + `.ics` needed to send a real confirmation / reschedule / cancel
- Multi-calendar selection UI, calendar-picker, or writing to any calendar other than the host's primary
- Host self-serve creation/editing of event types (event types remain fixture-defined per owner and are materialized for an owner at sign-in; slugs are data, not a CRUD surface)
- Payments, SMS, reminders, buffer rules, round-robin / collective across hosts beyond the group-capacity check already in scope
- A background job runner / queue for email retry or for lifecycle reconciliation — retry and reconciliation are idempotent HTTP routes the guest or owner can hit from the confirmation page; no cron, no queue
- Exactly-once email delivery — at-least-once with a documented, bounded duplicate window (AC-13 / REV1-07)
- Changing the proof harness shape: `PROOF_CMD` remains `npm test` (typecheck + `next build` + unit tests via `scripts/proof.cjs`); the builder never edits `.github/`

## Interface contracts (normative; ACs reference these)

### C1. Owner-scoped identity (REV1-01, REV1-02)

- Every event type belongs to exactly one owner. Uniqueness in `lib/availability/event-type.ts` becomes `(ownerId, slug)`, not global `slug`. `createEventType` takes `ownerId`; existing fixture/test callers default to the demo owner.
- Stable identifiers are deterministic strings derived from slugs, identical in memory and pg mode: owner `own_{ownerSlug}`, event type `evt_{ownerSlug}__{eventSlug}`, schedule `sch_{ownerSlug}__{scheduleKey}`. Re-seeding fixtures in a fresh isolate reproduces the same ids, so a booking's persisted `eventTypeId`/`scheduleId` always resolves, and group-capacity counts never split across isolates.
- Owner records are created/updated on host sign-in: the OAuth callback upserts `owners` (slug = validated local-part of the Google email, `firstName` = profile `given_name`, `email`, `calendarId = 'primary'`) and materializes that owner's fixture-defined event types and schedule with the ids above. The `demo` owner is seeded by migration and by `ensureDemoFixtures()`.

### C3. Booking response envelope (REV1-06)

The shipped client (`lib/api/client.ts`) expects `{ booking: { … start … } }` on 201 and recognises 409 codes `slot_unavailable` and `session_full`. Rev 2 keeps that envelope and **adds** fields; it does not introduce `slot_taken`/`slot_full` (those names from rev 1 are withdrawn):

```json
201 {
  "booking": { "id", "token", "ownerSlug", "eventSlug", "start", "end", "status", "revision", "hostFirstName", … },
  "delivery": {
    "email":    "sent" | "failed" | "pending",
    "calendar": "created" | "failed" | "skipped",
    "errors":   { "email"?: "gmail_send_failed" | "host_not_connected", "calendar"?: "calendar_insert_failed" | "host_not_connected" }
  }
}
409 { "error": "slot_unavailable" }   // overlap for this host (AC-4)
409 { "error": "session_full" }       // group capacity reached (AC-8)
409 { "error": "booking_changed" }    // versioned update lost (AC-18)
409 { "error": "operation_in_progress" }
503 { "error": "availability_unknown" }        // AC-7
503 { "error": "booking_outcome_unknown", "retryAfterSeconds": n }  // AC-11
```

`PublicBooking` in `lib/api/types.ts` gains `ownerSlug`, `eventSlug`, `revision`, `delivery`; `mapBooking` tolerates the additions. The client's `createBooking` posts to the owner-scoped route and maps `delivery` through; the form's success path navigates on any 201 regardless of `delivery.email`.

### C4. Notification policy (REV1-05)

- **Recipients are a product constant, not a mode:** confirm, reschedule, and cancel each email **both** invitee and owner (P3). No `none | invitee | owner | both` mode exists or is introduced.
- **`notificationMode` (existing `calendar_invitation | email_confirmation`) selects only the Google attendee behaviour:** `calendar_invitation` → the calendar event lists the invitee as an attendee and `events.insert/patch/delete` are called with `sendUpdates=all` (Google sends its native invite/update/cancellation in addition to Marlo's emails); `email_confirmation` → no attendees, `sendUpdates=none`. Default for fixture event types is `email_confirmation`.
- **Calendar occupancy (insert on book, patch on reschedule, delete on cancel) is unconditional** in both modes and in both mock and live adapters.
- `dispatchBookingNotification` and `tests/notification.test.ts` are updated to this policy; the mock email adapter records `{ action, revision, recipient }` per send.

### C5. Delivery ledger (REV1-07)

`notification_deliveries (booking_id, revision, action, recipient) PK` with `state ∈ {claimed, sent, failed}`, `claimed_at`, `attempts`. One row per (revision, action, recipient); `revision` is the booking row's monotonically increasing `revision` column. Initial delivery and retries share one **atomic claim**:

```sql
INSERT INTO notification_deliveries (booking_id, revision, action, recipient, state, claimed_at, attempts)
VALUES ($1,$2,$3,$4,'claimed',now(),1)
ON CONFLICT (booking_id, revision, action, recipient) DO UPDATE
  SET state='claimed', claimed_at=now(), attempts=notification_deliveries.attempts+1
  WHERE notification_deliveries.state='failed'
     OR (notification_deliveries.state='claimed' AND notification_deliveries.claimed_at < now() - interval '2 minutes')
RETURNING attempts;
```

Only a caller that gets a row back sends. Finalisation is `UPDATE … SET state=$s WHERE booking_id=$1 AND revision=$2 AND action=$3 AND recipient=$4 AND state='claimed'`. A send for `(revision, action)` older than the booking's current `(revision, latestAction)` is refused before claiming (409 `stale_revision`) so a late confirmation can never mark a reschedule/cancel delivery sent or send stale content after a cancel. The in-memory store implements identical semantics with a synchronous map. **Unavoidable ambiguity:** if Gmail accepts the message and the `sent` write then fails, the row stays `claimed` and becomes re-claimable after 2 minutes → at most one duplicate per recipient per 2-minute stale window; documented in README. `delivery.email` summarises the current revision's rows: `sent` iff all recipients `sent`; `failed` if any `failed`; `pending` if any `claimed` and none `failed`.

### C6. Lifecycle state machine (REV1-08, REV1-09, REV1-10)

`bookings` carries `status ∈ {confirmed, cancelled}`, `revision int`, `google_event_id`, and `pending_op jsonb` (`null` or `{ kind: "reschedule" | "cancel", newStart?, newEnd?, oldEventId?, startedAt }`). Create, reschedule, and cancel all begin with the **same per-host serialization boundary**: `SELECT pg_advisory_xact_lock(hashtext($hostId))` in pg mode, a per-host async mutex in memory mode; under it they `SELECT … FOR UPDATE` the booking (lifecycle ops) and re-read `status`, `revision`, and `pending_op`. Every state-changing `UPDATE` is conditional on `id AND revision = $expected AND status = 'confirmed'`; zero rows → 409 `booking_changed`.

**Create:** lock → conflict/capacity check → `INSERT` (app-generated `id` and `token`, `google_event_id NULL`) → `calendar.insert` (attendees per C4) → `UPDATE google_event_id` → `COMMIT` → release lock → email (C5). On a `COMMIT` exception the adapter classifies it: a **definite rollback** (server-reported error with SQLSTATE class ≠ `08`, or any error raised before `COMMIT` was sent) → `calendar.delete(eventId)` compensation, 500 `booking_failed`; an **unknown outcome** (SQLSTATE class `08`, socket `ECONNRESET`/`ETIMEDOUT`, or no server response) → reconcile on a fresh connection with `SELECT id FROM bookings WHERE id=$1`: row present → treat as committed and continue (201); row absent → definite rollback → compensate; reconcile itself fails → **no compensation**, log `orphan_unresolved { bookingId, eventId }`, respond 503 `booking_outcome_unknown` with no token. The fake DB models all three outcomes.

**Reschedule:** T1 (under lock): re-read FOR UPDATE; reject unless `status='confirmed'` and (`pending_op IS NULL` or `pending_op.kind='reschedule'` and stale > 2 min → resume); availability check for the new slot excluding this booking's own occupancy; `UPDATE pending_op = {kind:'reschedule', newStart, newEnd, oldEventId}` (versioned) → `COMMIT`. Calendar: `events.patch(oldEventId, newTime)`; on 404/410 → `events.insert` and remember the new id. T2 (under lock): `UPDATE start, end, rescheduled_from, google_event_id, revision=revision+1, pending_op=NULL WHERE id AND revision=$r AND pending_op->>'kind'='reschedule'` → `COMMIT` → email (`action=reschedule`, new revision). Failures: patch/insert fails → T2′ clears `pending_op`, booking unchanged, 502 `calendar_patch_failed` (retryable, no email). T2 definite failure → compensate (`patch` back to old time, or `delete` the fallback-inserted id), `pending_op` stays for resume, 500 `reschedule_failed`. T2 unknown → reconcile by re-reading `revision`: advanced → success path; not advanced → compensate as above. Email failure after T2 → 200 with `delivery.email: failed`; retry via notify route.

**Cancel:** T1 (under lock): re-read FOR UPDATE; reject unless confirmed (409 `booking_changed` if a concurrent reschedule advanced `revision`); `UPDATE pending_op = {kind:'cancel', oldEventId}` (versioned) → `COMMIT`. Status stays `confirmed` and capacity stays held until the event is gone. Calendar: `events.delete(oldEventId)` (404/410 tolerated). T2 (under lock): `UPDATE status='cancelled', revision=revision+1, pending_op=NULL WHERE id AND revision=$r AND pending_op->>'kind'='cancel'` → `COMMIT` → email (`action=cancel`). Failures: delete fails → T2′ clears `pending_op`, booking still confirmed, 502 `calendar_delete_failed` (retryable). T2 definite/unknown failure after a successful delete → `pending_op` stays; the next cancel call resumes at T2 (delete of an already-deleted event is a tolerated 404), so the retry response is 200 `cancelled`. A reschedule that reads `pending_op.kind='cancel'` is refused with 409 `operation_in_progress` — **no replacement event is ever inserted for a booking under cancellation** (REV1-08).

### C7. Calendar busy classification (REV1-03, REV1-04)

- External busy for the host's **primary** calendar is computed from `events.list` (`calendarId=primary`, `timeMin/timeMax` = the availability window, `singleEvents=true` so recurring series are expanded, `showDeleted=false`, `maxResults=250`, and a `pageToken` loop until `nextPageToken` is absent). An item is **managed** iff `extendedProperties.private.marloBookingId` is present (set on every Marlo insert/patch); managed items are excluded — managed occupancy comes only from the store. Every other item with `status != 'cancelled'` and `transparency != 'transparent'` is external busy; `dateTime` bounds are used as-is, all-day `date` bounds are converted in the host's timezone.
- `freeBusy.query` remains the read path for the existing multi-host (collective) availability in `lib/calendar/google-freebusy.ts`, and its fail-closed handling (AC-7) stays. Therefore the consent scope set is **exactly** `openid email profile https://www.googleapis.com/auth/calendar.freebusy https://www.googleapis.com/auth/calendar.events https://www.googleapis.com/auth/gmail.send` with `access_type=offline`, `prompt=consent` (REV1-04).
- Both `events.list` and `freeBusy` are fail-closed: non-2xx, a page that cannot be parsed, an item missing `start`/`end`, or a pagination loop that errors mid-way → `AvailabilityUnknown` → 503 `availability_unknown`.

### C8. Schema and migrations (REV1-11)

`sql/001_init.sql` is the complete initial schema for an **empty** database: `schema_migrations(version pk, applied_at)`, `owners(id pk, slug unique, first_name, email unique, calendar_id, created_at)`, `host_tokens(owner_id pk fk owners, refresh_token_enc bytea, updated_at)`, `event_types(id pk, owner_id fk, slug, kind, duration_min, capacity, notification_mode, schedule_id, unique(owner_id, slug))`, `availability_schedules(id pk, owner_id fk, timezone, rules jsonb)`, `bookings(id pk, token unique, owner_id fk, event_type_id fk, host_id, start timestamptz, "end" timestamptz, status, revision int default 1, google_event_id, rescheduled_from timestamptz, pending_op jsonb, invitee_name, invitee_email, notes, metadata jsonb, created_at)` with indexes `bookings(host_id, start)`, `bookings(event_type_id, start) where status='confirmed'`, `bookings(token)`; `notification_deliveries` per C5; and a seed `INSERT` for owner `demo` + its event type/schedule under the C1 ids. `scripts/migrate.cjs` (`npm run db:migrate`) applies `sql/*.sql` in filename order inside one transaction each, skipping versions already in `schema_migrations`. The pg store checks `schema_migrations` on first use and refuses to serve with `store_not_migrated` when the latest `sql/` version is missing; `/api/health` reports `schema`. README orders it: set `DATABASE_URL` → `npm run db:migrate` → set `LIVE_*`.

## Approach

Work proceeds in the order below; each step lands with its tests so `npm test` is green at every step.

### 1. Env + proof hardening first (AC-6, AC-15; LIVE-03, LIVE-09, REV1-12)
- `lib/env.ts` is the single reader: `resolveEnv(overrides?)` with `setEnvOverride()` for tests; `MARLO_PROOF=1` forces `store=memory, calendar=mock, email=mock`.
- `scripts/proof.cjs`: extract `provisionDependencies()` (the existing `npm ci` fallback) and `runProof()`; provisioning runs first, logs the network step, and exits 2 under `MARLO_OFFLINE=1`; `runProof` spawns typecheck/build/unit with the explicit disabled child env. Export the functions for the unit test (guarded by `require.main === module`). `.github/proof.yml` is not touched.
- Test-setup `fetch` guard throws on any non-localhost URL; grep test exception list contains only `app/api/health/route.ts`.

### 2. Owner-scoped identity + per-owner routing + host chrome (AC-1, AC-2, AC-14; P1, REV1-01, REV1-02)
- `lib/owners.ts`: `Owner { id, slug, firstName, email, calendarId }`, `stableIds(ownerSlug, eventSlug, scheduleKey)` (C1), `OwnerStore` (memory + pg), `resolveOwner(slug)`. `ensureDemoFixtures()` and the OAuth callback both go through `materializeOwner(owner)` which upserts the owner and its fixture-defined event types/schedule under stable ids.

## Assumptions and risks

- **Assumption:** the host's Google account grants `calendar.freebusy`, `calendar.events`, and `gmail.send` in one consent; sending "as the host" via Gmail API is acceptable to the Founder for this slice (no custom domain / SES).
- **Assumption:** an owner's slug is the validated local-part of their Google email; a collision on sign-in (two accounts with the same local-part) fails the sign-in with `owner_slug_taken` rather than silently suffixing. Documented in README.
- **Assumption:** `events.list` on the host's primary calendar returns every occupying item within the window when `singleEvents=true` is used; items on secondary calendars are out of scope (Non-goals).
- **Risk — Next env reload (LIVE-03):** `next build` re-reads `.env.local`; mitigated by the explicit disabled child env plus `MARLO_PROOF=1` hard override; the fetch guard fails the proof loudly rather than silently going live.
- **Risk — Neon advisory locks under pooling:** `pg_advisory_xact_lock` is transaction-scoped and safe under PgBouncer transaction pooling; the builder must not use session-level locks. The lock is held across the Google `events.insert` call on create (bounded by the adapter timeout, 10 s); accepted for this slice.
- **Risk — at-least-once email:** a Gmail-accepted send whose `sent` write fails is re-sent after the 2-minute stale window (C5); accepted and documented.
- **Risk — `pending_op` stuck when a process dies mid-operation:** resumed by the next same-kind call; a different-kind call is refused with `operation_in_progress` until the stale window elapses, after which the stuck op is reconciled first. No background reconciler by design.
- **Risk — Google patch vs host deletion race on reschedule:** a 404/410 on patch inserts a replacement; a duplicate is possible only if the host manually re-adds the event — accepted.
- **Risk — encryption key rotation:** `OAUTH_TOKEN_KEY` rotation is not handled; documented as a manual re-connect.
- **Scope risk:** AC-1/2/10 touch the front-end shipped in BOOK-FE (#38). The builder must keep the BOOK-FE mobile/CSS tests green; no visual redesign.
